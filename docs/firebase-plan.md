# План: облачное сохранение прогресса через Firebase

> Статус: **план, ещё не реализован**. Документ описывает, что и в каком порядке делаем, кто что делает (вы в консоли Firebase или Claude в коде) и как проверяем результат.

## 1. Цель и итоговые решения

**Сейчас.** Прогресс хранится только в `localStorage` браузера (`kotomatika/js/storage.js`, ключ `kotomatika.v1`). Если очистить браузер, сменить телефон или открыть игру на планшете, всё пропадёт.

**Хотим:**
1. Прогресс автоматически сохраняется в облако и сам подтягивается на другом устройстве.
2. Можно восстановить прогресс на новом устройстве и откатиться к резервной копии за прошлые дни.
3. Игра по-прежнему работает без интернета: облако — дополнение, а не обязательное условие.
4. Ребёнок не заводит никаких аккаунтов, вход делает родитель один раз на устройство.

| Вопрос | Решение | Почему |
|---|---|---|
| База данных | **Cloud Firestore** | Документная база, есть офлайн-кэш и подписка на изменения в реальном времени. Профиль игрока — один документ JSON. |
| Вход | **Firebase Authentication**: Google-вход родителя, запасной вариант — вход по ссылке на e-mail | Ребёнку не нужен аккаунт, данные принадлежат родителю. Так проще и с точки зрения правил о детских данных. |
| Модель | «Семья» = аккаунт родителя; внутри — профили детей | Как сейчас: несколько игроков на устройстве, у каждого свой код из картинок. |
| Синхронизация | **Сначала локально** (local-first): `localStorage` остаётся основным, облако догоняет | Игра не тормозит и работает офлайн. |
| Конфликты | Умное слияние по полям (см. §5) | Если ребёнок играл на двух устройствах, звёзды и награды не теряются. |
| Резервные копии | Ежедневный снимок профиля, хранится 30 дней | Можно откатиться, если что-то пошло не так. |
| Хостинг | **Firebase Hosting + автодеплой из GitHub Actions** | См. §2. |
| Серверный код (Cloud Functions) | **Не нужен** на первом этапе | Всё решают правила безопасности, минимум затрат и движущихся частей. |

## 2. Хостинг: оставаться на GitHub Pages или переезжать?

**Рекомендация: переехать на Firebase Hosting и настроить автоматическую доставку из GitHub.** Тогда игра, база и вход живут в одном проекте Firebase.

| | GitHub Pages | Firebase Hosting |
|---|---|---|
| Работает ли с Firestore/Auth | Да, нужно добавить `yurafilionchik.github.io` в Authorized domains | Да, домен `*.web.app` разрешён сразу |
| Автодеплой | Уже есть (ветка `main`) | GitHub Action: пуш в `main` — сразу на сайт |
| Предпросмотр изменений | Нет | **Да**: каждый PR получает свою временную ссылку (preview channel) |
| Заголовки кэша | Нельзя настроить | Настраиваются в `firebase.json` |
| Откат версии | Через git revert | В один клик в консоли (история релизов) |
| Свой домен | Можно | Можно, SSL выдаётся автоматически |
| Цена | Бесплатно | Бесплатный лимит с большим запасом для такой игры |

### ⚠️ Важная ловушка при смене домена

`localStorage` привязан к домену. На новом адресе (`kotomatika.web.app`) прогресс со старого (`yurafilionchik.github.io`) **не будет виден**. Поэтому порядок такой:

1. Сначала выпускаем облачное сохранение **на GitHub Pages** (фаза 3).
2. Родитель входит в аккаунт на старом адресе, и прогресс уходит в облако.
3. Только потом переключаемся на Firebase Hosting (фаза 5). На новом адресе родитель входит в тот же аккаунт, и прогресс загружается.
4. Старый адрес на GitHub Pages заменяем страницей-переадресацией, но **после** того, как прогресс перенесён.

На всякий случай делаем ещё и экспорт/импорт сохранения файлом (фаза 2). Это ручной запасной путь, который не зависит от Firebase.

## 3. Модель данных Firestore

```
families/{uid}                          ← документ семьи (uid родителя из Firebase Auth)
  ├─ createdAt, updatedAt, schemaVersion
  └─ profiles/{profileId}               ← один документ = один ребёнок (≈10–30 КБ)
        ├─ data: { ...весь профиль как в localStorage... }
        ├─ rev: number                  ← номер ревизии, растёт при каждой записи
        ├─ updatedAt: serverTimestamp
        ├─ updatedBy: deviceId          ← какое устройство записало
        ├─ schemaVersion: 1
        └─ snapshots/{YYYY-MM-DD}       ← ежедневная резервная копия
              ├─ data, rev, createdAt
              └─ expireAt               ← TTL-политика удаляет через 30 дней
```

Решения по полям:
- **Код из картинок (`pin`) в облако не кладём открытым текстом.** Храним `pinHash = SHA-256(profileId + ":" + pin)`. Это не криптографическая защита (комбинаций всего 729), а защита от случайного подглядывания. Настоящая защита данных — правила безопасности: читать их может только аккаунт семьи.
- Профиль хранится целиком в поле `data`. Документ Firestore вмещает до 1 МБ, а наш профиль весит десятки килобайт. Одна запись на сохранение — дёшево и просто.
- `deviceId` — случайный идентификатор устройства в `localStorage`. Нужен, чтобы отличать свои записи от чужих в подписке на изменения.

## 4. Архитектура в коде

```
kotomatika/js/storage.js   ← как сейчас (localStorage), плюс событие «профиль изменён» и метки rev/dirty
kotomatika/js/cloud.js     ← НОВЫЙ: ES-модуль, грузит Firebase SDK с gstatic, вход, синхронизация
kotomatika/js/merge.js     ← НОВЫЙ: чистая функция слияния двух версий профиля (покрыта тестами)
kotomatika/js/parent.js    ← НОВЫЙ: «Родительский уголок» (вход, статус, резервные копии, экспорт)
kotomatika/firebase-config.js ← НОВЫЙ: публичный конфиг веб-приложения Firebase
```

Принципы:
- **Игра не зависит от облака.** `cloud.js` подключается как `<script type="module">`. Если SDK не загрузился (нет сети, файл открыт через `file://`), игра работает как раньше, только без значка ☁️.
- **Одна точка встраивания.** Все 28 вызовов сохранения уже идут через `Store.save()`. Добавляем туда `Store.onChange(cb)`: модуль облака подписывается и сам решает, когда отправить данные.
- **Firebase SDK** — модульная версия с CDN `https://www.gstatic.com/firebasejs/<версия>/...`. Номер версии фиксируем явно (актуальный берём из документации Firebase в момент внедрения). Сборщик (npm/webpack) не нужен, проект остаётся «чистым HTML/JS».
- **Конфиг Firebase не секретный.** `apiKey` веб-приложения — публичный идентификатор, его можно коммитить. Данные защищают правила безопасности, App Check и ограничение API-ключа по доменам (см. §7).

### Алгоритм синхронизации

```
При старте:
  1. Store.load() из localStorage — играть можно сразу.
  2. cloud.js ждёт onAuthStateChanged. Если родитель не входил, синхронизации нет.
  3. Если вход есть: подписка onSnapshot на families/{uid}/profiles.
     - профиль есть только в облаке   → добавить на устройство (новое устройство / восстановление)
     - профиль есть только локально   → загрузить в облако (первый вход)
     - есть в обоих местах             → merge(local, remote) → сохранить результат в оба места

При игре:
  4. Store.save() → помечаем профиль dirty → отложенная запись в облако через 5 секунд
     (debounce: за серию ответов уходит одна запись, а не двадцать).
  5. Принудительная отправка при visibilitychange = hidden / pagehide (ребёнок закрыл вкладку).
  6. Запись — транзакция: читаем rev в облаке; если он больше нашей базовой ревизии,
     сначала merge, потом пишем rev+1. Так два устройства не затрут друг друга.
  7. Не пишем, если данные не изменились (сравниваем хэш JSON).

Резервная копия:
  8. При первой записи за день дополнительно пишем snapshots/{сегодня} с expireAt = +30 дней.
```

Офлайн: Firestore SDK сам ставит записи в очередь и отправит их при появлении сети. Дополнительно включаем постоянный кэш (`persistentLocalCache`), чтобы очередь пережила перезагрузку вкладки.

## 5. Слияние профилей (если играли на двух устройствах)

Чистая функция `mergeProfiles(a, b)` в `merge.js`. Правила подобраны так, чтобы ребёнок **никогда не терял достижения**:

| Поля | Правило |
|---|---|
| `xp`, `totalCorrect`, `totalWrong`, `bestCombo`, `blitzBest`, `bossWins`, `bossLevel`, `perfectCount`, `purchases`, `farm.harvested` | максимум из двух |
| `stars`, `colStars` | максимум по каждому миру/уровню |
| `achievements` | объединение (берём раннюю дату) |
| `owned`, `pets`, `breedsSeen` | объединение множеств |
| `facts` (выученные примеры) | по каждому примеру берём версию с бо́льшим числом ответов `r + w` |
| `streak` | `best` = максимум; `count`/`lastDate` — из версии с более поздней `lastDate` |
| `daily` | из версии с более поздней датой; при одинаковой дате `correct` = максимум |
| `fish`, `farm.food`, `farm.pond`, `farm.size`, `cat`, `pet`, `settings`, `name`, `pinHash` | из более новой ревизии (`updatedAt`) — это «тратящиеся» и выбранные вещи, их нельзя складывать |

Тесты (Node, встроенный `node:test`, без зависимостей):
- слияние с самим собой ничего не меняет;
- порядок аргументов не влияет на результат;
- звёзды, награды, питомцы и купленные вещи из обеих версий сохраняются;
- рыбки и наряд берутся из более новой версии;
- профиль старого формата (без новых полей) сливается без ошибок (через `migrate`).

## 6. Интерфейс

**Родительский уголок** (⚙️ → «Для родителей»). Вход защищён «родительским вопросом» — пример, который ребёнку 9 лет решить сложно, например `37 × 6`.
- «Войти через Google» / «Войти по ссылке на почту»
- Статус: ☁️ «Сохранено в облаке · 2 мин назад» / «Нет сети — сохраним позже» / «Не подключено»
- Список устройств с датой последней записи (по `updatedBy`)
- **Резервные копии**: список дат за 30 дней → «Восстановить». Перед восстановлением текущая версия тоже сохраняется как копия.
- **Экспорт в файл** (`kotomatika-Маша-2026-10-12.json`) и **импорт из файла** — работают без Firebase.
- «Выйти из аккаунта на этом устройстве» (локальный прогресс остаётся)

**В игре:**
- Маленький значок ☁️ возле рыбок в меню: зелёный — сохранено, серый — офлайн.
- На экране «Кто играет?» на новом устройстве: «Есть сохранения в облаке? Попроси родителей войти» → профили появляются сами.
- Если на двух устройствах заведены разные профили с одинаковым именем: диалог «Объединить Машу и Машу?» → `mergeProfiles`.

## 7. Безопасность и защита от лишних трат

**Правила Firestore** (`firestore.rules`):

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isOwner(uid) { return request.auth != null && request.auth.uid == uid; }

    match /families/{uid} {
      allow read, write: if isOwner(uid);

      match /profiles/{profileId} {
        allow read, delete: if isOwner(uid);
        allow create, update: if isOwner(uid)
          && request.resource.data.keys().hasOnly(['data', 'rev', 'updatedAt', 'updatedBy', 'schemaVersion', 'pinHash'])
          && request.resource.data.rev is int
          && (resource == null || request.resource.data.rev == resource.data.rev + 1)
          && request.resource.data.updatedAt == request.time
          && request.resource.data.data.name is string
          && request.resource.data.data.name.size() <= 14;

        match /snapshots/{day} {
          allow read, delete: if isOwner(uid);
          allow create, update: if isOwner(uid) && day.matches('^\\d{4}-\\d{2}-\\d{2}$');
        }
      }
    }
  }
}
```

Остальное:
- **App Check** (reCAPTCHA Enterprise или v3) — запросы к базе принимаются только от нашей страницы. Сначала включаем в режиме наблюдения, потом в режиме блокировки.
- **Ограничение API-ключа** в Google Cloud Console: только HTTP-рефереры `kotomatika.web.app`, `*.firebaseapp.com`, `yurafilionchik.github.io` (пока идёт переезд), `localhost`.
- **Бюджет и оповещения** в Google Cloud Billing: например, порог $5 в месяц с письмами на 50/90/100%. Наш реальный расход ожидается около $0 (см. §9). Оповещение нужно на случай ошибки в коде — например, бесконечного цикла записей.
- **Защита от цикла записей в коде**: не чаще 1 записи в 5 секунд на профиль, не больше ~500 в сутки на устройство. При превышении синхронизация останавливается и пишет предупреждение в консоль.
- **Минимум данных о ребёнке**: в облаке только игровое имя и игровой прогресс. Никаких фото, возраста, школы. Аккаунт принадлежит родителю.

## 8. Хостинг и автоматическая доставка

`firebase.json` в корне репозитория:

```json
{
  "hosting": {
    "public": ".",
    "ignore": ["firebase.json", "firestore.rules", "firestore.indexes.json", "**/.*", "**/node_modules/**", "docs/**", "tests/**", "README.md"],
    "headers": [
      { "source": "**/*.@(js|css|html|webmanifest)", "headers": [{ "key": "Cache-Control", "value": "no-cache" }] },
      { "source": "**/*.@(svg|png|jpg|webp)", "headers": [{ "key": "Cache-Control", "value": "public, max-age=604800" }] }
    ]
  },
  "firestore": { "rules": "firestore.rules", "indexes": "firestore.indexes.json" }
}
```

`no-cache` для js/css нужен потому, что у нас нет сборки с хэшами в именах файлов. Браузер каждый раз сверяет версию (дёшево, через ETag) и не застревает на старом коде после обновления.

GitHub Actions (`.github/workflows/`):

| Файл | Когда | Что делает |
|---|---|---|
| `firebase-deploy.yml` | push в `main` | тесты → деплой правил Firestore → деплой Hosting (live) |
| `firebase-preview.yml` | pull request | тесты → деплой во временный preview-канал → комментарий в PR со ссылкой (живёт 7 дней) |
| `tests.yml` | push / PR | `node --test` (слияние) + проверка правил на эмуляторе Firestore |

Деплой использует официальный `FirebaseExtended/action-hosting-deploy` и секрет `FIREBASE_SERVICE_ACCOUNT_<ID_ПРОЕКТА>`. Команда `firebase init hosting:github` создаёт сервисный аккаунт и секрет автоматически. Для деплоя правил сервисному аккаунту добавляем роль *Firebase Rules Admin*.

Итог: вы мержите PR или пушите в `main` → через 1–2 минуты новая версия на `https://<проект>.web.app`, правила базы обновлены. Для каждого PR есть отдельная ссылка, где можно попробовать изменения до выхода.

## 9. Стоимость (оценка)

Бесплатных лимитов Firestore и Hosting с большим запасом хватает на семью из нескольких детей. Точные лимиты сверяем на странице цен Firebase в момент внедрения, они меняются.

| Ресурс | Наша оценка на 1 ребёнка в день | Порядок бесплатного лимита |
|---|---|---|
| Записи Firestore | ~50–150 (debounce 5 с + снимок) | десятки тысяч в день |
| Чтения Firestore | ~10–50 (старт + подписка) | десятки тысяч в день |
| Хранилище | ~30 КБ профиль + 30 снимков ≈ 1 МБ | ~1 ГБ |
| Трафик Hosting | ~300 КБ за загрузку игры | сотни МБ в день |

Подключённый биллинг (тариф Blaze) нужен только как условие для некоторых функций. При таких объёмах ожидаемый счёт — $0. Бюджетное оповещение (§7) страхует от сюрпризов.

## 11. Тестирование

| Что | Как |
|---|---|
| Слияние профилей | `node --test tests/` — юнит-тесты, в CI на каждый PR |
| Правила безопасности | `@firebase/rules-unit-testing` + эмулятор Firestore: чужой uid не читает и не пишет; rev только +1; лишние поля отклоняются |
| Синхронизация | Playwright с эмулятором Auth и Firestore: два браузерных контекста = два устройства; играем в одном и проверяем, что во втором появились звёзды |
| Офлайн | Playwright `context.setOffline(true)` → играем → включаем сеть → запись дошла |
| Миграция старых сохранений | Фикстура профиля «до облака» → загрузка → проверка полей |
| Ручная приёмка | Чек-лист фазы 3 на реальных телефоне и планшете |

## 12. Риски и как их закрываем

| Риск | Что делаем |
|---|---|
| Потеря прогресса при смене домена | Сначала облако на старом домене, потом переезд + экспорт в файл (§2) |
| Два устройства затирают друг друга | Транзакция с `rev` + слияние по полям (§4, §5) |
| Ошибка в коде вызывает лавину записей и счёт | Debounce, лимит частоты, бюджетное оповещение (§7) |
| Ребёнок нажал «Выйти» или «Удалить» | Действия только в родительском уголке за «родительским вопросом»; снимки за 30 дней |
| Firebase недоступен или нет сети | Local-first: игра работает, облако досинхронизирует позже |
| Утечка конфига Firebase | Это не секрет; доступ закрыт правилами, App Check и ограничением ключа |
| Новые поля профиля в будущих обновлениях | `schemaVersion` + существующий `migrate()` + тест на старую фикстуру |
